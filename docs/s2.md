# S2 candidate: bounded mutations and full-user execution

This is paired with the house S2 mutation-plane API. It is not a Dell
installation or Linux v0 acceptance receipt.

## Protocol

The house persists an operation before dispatch. Write and execute additionally
require an exact-size temporary HTTP input (8 MiB maximum); the device consumes
it once with its credential and epoch/revision. Both local and remote grants
are checked before downloading. A lost response is never replayed.

File operation metadata:

- mkdir: volume, relative path.
- write: volume, path, mode=create/overwrite/append, input_size; raw input bytes.
- copy/move: source_volume, source_path, destination volume/path.
- rename: volume, path, destination.
- trash: volume, path, existing quarantine directory.
- execute: input_size, timeout_seconds (1–300, default 30).

Execute input is strict UTF-8 JSON `{argv: [...], cwd: "/absolute/path",
stdin_base64: "optional base64"}`; no unknown keys, NULs or implicit shell.
Argv is capped at 1024 entries / 1 MiB total / 128 KiB each. The entire encoded
input is bounded by 8 MiB. Execute is general service-user authority, not a
volume sandbox. The execute tool requires its separate explicit grant, but that
is not an assurance that file writes cannot execute code: **write on a volume
containing the user's home is deferred code execution as that user**. Shell
startup files, autostart entries, SSH authorized keys and git hooks can run code
on later use/login without an execute-tool grant. A broad root-volume write
grant has the same consequence.

**An execute grant can rewrite `state.json` and the local ceiling.** Once
execute is granted, the ceiling is not a sandbox or security limit on that
resident's general service-user authority. The two grants authorize tool
dispatch; they do not constrain arbitrary programs running as that OS user.

Results preserve binary stdout/stderr as base64, with at most 1 MiB per stream,
truncation flags and exit status. No argv/stdin/output is a log field.

## Filesystem semantics

Primitives retain S1 fd-rooted containment, protected live-inode/ancestry checks
and mount-change denial. Writes use anonymous atomic staging; unsupported
`O_TMPFILE` fails closed. Overwrite replaces an existing singly-linked regular
file with a new 0600 inode, without preserving ACLs/xattrs. Append may commit a
prefix. Receipts report committed bytes and failed staging cleanup.

File tools deny the entire `~/.config/systemd` and
`~/.config/environment.d` subtrees, in addition to the companion's state,
unit and binary. This prevents unit drop-ins and user-manager environment
configuration (including `user.conf` and `user.conf.d`) from changing the
companion's ceiling enforcement on restart.
Missing protected directories are created locally before serving and captured
by inode; symlink/non-directory targets fail closed. This targeted protection
does not remove the deferred-execution authority of a home-volume write grant.

Copy is regular-file-only, no-overwrite and at most 8 MiB total. Cross-volume
move rechecks the unchanged source before unlinking after complete publication;
post-copy failure reports copied/source retained. Same-volume move uses
no-replace rename. No standalone permanent-delete tool exists.

**Directory rename/move/trash are refused**, as are multiply-linked mutations.
Trash requires a private owned writable 0700 directory on the same verified
mount; it never falls back to copying elsewhere. Its returned random name is
the quarantine receipt. Mkdir creates a single directory, not missing parents.

Hostile concurrent local writers remain outside this non-transactional
boundary: Linux rename/unlink cannot compare expected inode identity atomically.
Pinned handles/rechecks do not eliminate that race. Namespace power-loss
durability is not promised.

## Execute and removal

See `internal/runner/README.md` for systemd 254+ requirements, user-manager
environment, cgroup cleanup and ambiguous-start limits. Fake tests are not
proof of actual descendant-tree killing; the opt-in real test requires a
running ordinary user manager and must be run on the acceptance machine.

`companion uninstall --user [--state-dir DIR]` sets local deny, stops the user
service, revokes the current device credential remotely, durably clears its
credential, then disables/removes the unit. A non-secret ceiling/audit/removal
receipt remains for idempotent retry. Personal files and the binary are not
deleted. Failed remote revocation preserves credential material and local deny.
An unresolved lost credential-rotation response may require recovery or human
revocation first; there is no silent forced-removal mode.

## Recorded lifecycle follow-ups

The house deadline includes upload/download time. A runner timeout or bounded
cleanup can finish after that deadline, in which case late delivery is suppressed
and no partial-output receipt is delivered. A future change must reserve cleanup
and delivery time and distinguish a timed-out execution from supervision failure.
Until then, an absent/timed-out result must not be read as "the command did not
run".

The house input endpoint can currently return 201 after attachment even when
dispatch subsequently refuses; callers must inspect operation status, not treat
201 as execution. Pause/revoke make saved inputs inaccessible immediately but
leave their rows for the expiry sweep (up to ten minutes). Retry after uninstall
has removed the unit must be checked against actual systemd missing-unit stop/
disable behavior on the Dell; the current fake-systemctl test is not that proof.
These are tracked in repository issue #1 and the paired house issue #401.

## Remaining acceptance

Reciprocal review and paired integration gates precede merge. Dell SSH trust,
genuine human enrollment authority, actual mount/Btrfs identity and subvolume
protection, linger/restart and actual managed process-tree cleanup remain
unverified. Btrfs remains denied. Directory operation support is not complete
v0 support. No service has been installed by this source change.
Protected configuration paths currently assume the default `XDG_CONFIG_HOME`;
acceptance must verify the actual user-manager configuration root before enabling
write access. A non-default root needs matching protection, not an assumption
that the default paths cover it.
